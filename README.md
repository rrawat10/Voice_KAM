# Seller Studio — mini voice KAM

A browser voice assistant for the Snapdeal assignment. Native Gemini audio handles the conversation; a compact Gemini Flash planning call grounds each business turn in the selected table, seller statements, a running summary, and the last 15 conversation turns. If new arithmetic is needed, Python writes the result back into the same evidence collection and the planner makes one final response. The backend accepts a typed plan before releasing the corresponding business audio and updating the UI.

## Run locally (Windows)

From this directory:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
npm --prefix frontend ci
npm --prefix frontend run build
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --workers 1
```

Open http://127.0.0.1:8000. Data loading, Excel preview, validation, and the interface work without a Gemini key. Voice is visibly disabled until it is configured.

Set `GEMINI_API_KEY` in `.env`, then restart the server. Never put the key in frontend code or commit `.env`. Model access varies by project: `LIVE_MODEL` and `PLANNER_MODEL` are configurable. The defaults are `gemini-3.8-live` and `gemini-3.5-flash-lite`, with `PLANNER_THINKING_LEVEL=minimal`. The larger 3.8 Flash planner exceeded the eight-second deadline during initial testing; Flash-Lite is used for latency. If changing the planner, also choose a reasoning level supported by that model (3.8 Flash requires low, medium or high).

Gemini Live native audio automatically detects the spoken language and can switch languages in one conversation. The UI therefore does not force a language selector: sellers can speak English, Hindi, Hinglish, or another supported language. The planner is instructed to respond in the seller's language where it can do so reliably.

For UI development, run FastAPI on port 8000 and `npm --prefix frontend run dev` in another terminal. Vite proxies `/api` including the voice WebSocket. Use Chrome/Edge on HTTPS or localhost for microphone access.

## Data contract

Choose **Use mock data**, or download the Excel template and upload an `.xlsx` file. The first worksheet must have exactly these three headers:

| Metric | Last Month | This Month |
| --- | --- | --- |
| Sales | 200000 | 135000 |
| Orders | 400 | 270 |
| Cancellation rate | 8 | 14 |
| Average selling price | 500 | 500 |
| Out-of-stock products | 5 | 18 |

Supported: numeric values, INR strings with commas, explicit percentages (`14%`), and formatted Excel percentage cells. Missing metrics remain unknown; they never inherit mock values. At least one metric must have both periods. No formulas, duplicate metrics, negative values, arbitrary product tables, or hidden analysis of extra worksheets. Limits: 2 MB upload, 10 MB uncompressed workbook, 100 rows. Extra worksheets are explicitly ignored. Currency is INR.

The arithmetic yields a **32.5%** drop in assignment sales/orders, not 35%; cancellations rise by **6 percentage points**. The planner asks naturally about period timing only when it affects the seller's question, and it must not infer a causal sales loss from cancellation rates.

## Session and conversation architecture

- **WebSocket:** PCM microphone audio up; generated PCM audio and immediate playback controls down. The Gemini key stays on FastAPI.
- **SSE:** authoritative data snapshots, seller facts, questions, recommendations, transcripts, status and latency. Reconnection sends a fresh snapshot.
- **Memory:** one isolated, unguessable cookie-based session per browser. It retains a running, visible conversation summary and 15 complete seller/assistant turns, plus structured seller facts and the current plan. The summary refreshes in the background only once the transcript is substantial or old turns are removed, so it never delays voice playback. Python memory only. No Redis, MongoDB, signup, raw audio recording, or durable conversation database.
- **Questions:** generated by the LLM from the seller's current utterance, prior question, facts and table. There is no prewritten question tree or regex interpretation of human answers.
- **Disagreements:** the sheet remains unchanged; seller statements and unresolved issues live in ordinary session memory. The model asks naturally about updated numbers, period differences or corrections. A corrected seller number is attributed to the seller, not silently rewritten into calculated spreadsheet metrics.
- **Validation:** Python computes metrics; Pydantic checks structure; quote and evidence checks reject unsupported references and typed metric values. These checks do not prove every semantic claim in a model response.
- **Mid-conversation calculation:** the model can request difference, percentage change or ratio using source references. Python executes at most two operations in one batch, checks units and zero denominators, and saves the results alongside spreadsheet numbers in `dataset.evidence`, with input provenance. A second planning pass can explain them; no further calculation loop is allowed. Hypothetical or seller-stated inputs stay labelled. Results disappear when an input is corrected. The UI shows the calculation and actual activity events, not private model reasoning.
- **Turn handling:** per-session lock, turn epochs, stale-result checks, one concurrent voice connection per session, and interruption playback clearing.

Run **exactly one Uvicorn worker**. A server restart erases all sessions. Sessions expire after 30 minutes of inactivity, refreshed on accepted conversation turns; background cleanup runs every 5 seconds. Closing a tab or a temporary network disconnect does not delete the session. Loading a new dataset replaces the previous session. An anonymous HttpOnly cookie lasts 24 hours so a returning browser can receive an explicit expired-session notice rather than silently losing context. The cookie is only a random locator, not chat history. After the cookie itself expires, the visitor is indistinguishable from a new visitor. Different browser profiles have isolated sessions; tabs in the same profile share the cookie. Five-minute audio connections and two concurrent calls bound demo usage.

## Native deployment — no Docker required

Push this directory as the root of a Git repository. The built `frontend/dist` files are intentionally versioned: FastAPI serves them, so a native host only needs Python at deploy time. Create a native Python web service with:

- Build: use the default Python buildpack dependency install from `requirements.txt`.
- Start: `uvicorn backend.main:app --host 0.0.0.0 --port $PORT --workers 1`.
- Environment: `GEMINI_API_KEY`, `LIVE_MODEL`, `PLANNER_MODEL`, `SECURE_COOKIES=true`.
- Health check: `/api/health`.
- Support for HTTPS, WebSockets and unbuffered SSE; one server instance.

`render.yaml` is a native Render blueprint. If committing the surrounding Snapdeal directory instead, set the service root directory to `voice-kam`. A free sleeping host is suitable for basic testing but adds cold-start latency; warm it before a demo, or choose a small always-on instance. The frontend is served by FastAPI, so there is only one origin and service to configure. No hosting account or deployment is assumed to exist.

### Free demo hosting

For this in-memory demo, use **one** web-service instance and **one** Uvicorn worker. Koyeb is the best free option to try first: its documented free instance has 512 MB RAM, 0.1 vCPU and 2 GB SSD. That is sufficient for this app because Gemini performs the AI inference remotely, but it is not high-performance compute. Choose Git deployment, set the service root to `voice-kam`, then configure:

- Build command: leave blank (the Python buildpack installs `requirements.txt`)
- Run command: `uvicorn backend.main:app --host 0.0.0.0 --port $PORT --workers 1`
- Health check: `/api/health`
- Environment secrets: `GEMINI_API_KEY`, `LIVE_MODEL`, `PLANNER_MODEL`, and `SECURE_COOKIES=true`

Koyeb's current documentation lists Git-based Python deployment and the free-instance size. The frontend is already built and checked in, so select the Python buildpack; Node is only needed locally when changing the UI. Render is a workable alternative and supports WebSockets, but its free web service can sleep, so expect a cold start and loss of temporary in-memory sessions after restart. Railway supplies only limited credits after its trial. Do not use Vercel, Netlify or Cloudflare Workers for this current app: it needs a long-lived FastAPI process for WebSocket audio, SSE and temporary memory.

## Live acceptance checks when the key arrives

Initial live smoke test (11 November 2026): authentication, the configured Live connection, one business tool/planner turn, accepted session updates, and generated response audio passed using `python -m scripts.smoke_voice`. The planner took 4.96 seconds and first server audio arrived at 5.89 seconds after the synthetic text turn. This is one observation, not a latency guarantee or a microphone test. The 3–4 second target is not yet met. The larger 3.8 Flash planner previously timed out at eight seconds, including with low reasoning.

A follow-up test with instructions for shorter speech and compact JSON took 5.02 seconds in the planner and 5.95 seconds to first server audio. After moving summary refresh off the spoken path and reducing the critical response schema, one isolated planner benchmark took 2.64 seconds. A later full Live run varied to 7.02 seconds in the planner and 7.97 seconds to first server audio, while a previous compact full run measured 4.30 and 5.52 seconds. Remote provider capacity and generation variance dominate this range. The compact contract preserves evidence, exact seller quotes, typed metric references, calculator requests and Python validation; it removes repeated dashboard metadata from the pre-speech response. A strict four-second end-to-end guarantee is not established.

1. Verify audio output, tool call and structured planner output on the selected models.
2. Speak English and Hindi/Hinglish; check Indian numbers and interrupt midway through a reply.
3. Try: "I don't know", "that's wrong", "I can't afford ads", a revenue figure different from the sheet, and "just give me next steps".
4. Confirm new seller statements don't silently replace the data, no repeated answered question, and no invented traffic/competitor metrics or promised uplift.
5. Measure speech-end to first scheduled browser audio playback (target 3–4 seconds); separately inspect planner timing. The UI includes network time and browser playback scheduling. The local speech-end detector waits about 400ms for silence, so add this endpoint-detection delay when comparing against the last spoken sound. Hardware audio output delay is not measured.
6. Return before expiry and verify the state remains; after expiry, verify the notice and fresh-start behavior. Loading another dataset should replace the previous session. Record a real 1–2 minute conversation and submit a one-page workflow explanation.

## Honest prototype limits

No zero-hallucination claim: schema/evidence checks constrain the plan, but the voice model can paraphrase it and semantic claims still require evaluation. Streaming audio is not fully transcript-verified before playback. LLM/tool compliance and the 3–4 second latency target are unverified until real API/microphone testing. Each planner call has an 8-second timeout and no retry loop; a turn with a calculation can take longer because it needs a second call. Partial transcripts and acoustic turn boundaries can be imperfect. Calls stop after five minutes; reconnecting preserves only the current temporary application state, not an old provider audio stream. A final summary is requested conversationally; pausing does not trigger another generation.
